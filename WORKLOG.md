## 2026-11-25 — Карта диска WSL (treemap)

**Зачем.** WinDirStat, WizTree и подобные утилиты видят WSL как один файл `ext4.vhdx` и внутрь не заглядывают. Решено начать только с WSL, цвет — по типам файлов. Диски Windows можно добавить следующим шагом: модель и контрол от источника данных не зависят.

### Что сделано

- **Сканер `wsl/treescan.py`** (только стандартная библиотека).
  - Обходит `/`, не выходя на другие файловые системы (`st_dev`).
  - Считает занятое место по `st_blocks`, жёсткие ссылки учитывает один раз, символические ссылки не раскрывает.
  - Держит по 24 крупнейших файла на каталог; объекты меньше `total/60000` (не меньше 64 KiB) сворачиваются в узел «мелкие объекты».
  - Место, которое не удалось прочитать (нет доступа, метаданные ext4), выводится узлом «не учтено», чтобы карта сходилась с `df`.
  - Расширения: `libssl.so.3` сводится к `.so`, хеш-подобные суффиксы длиннее 10 символов считаются файлами без расширения.
- **Агент.**
  - Новый запрос `wsl-tree-request.json`, результат пишется в `wsl-tree.json` (оба рядом с основными файлами, имена фиксированы).
  - Сканирование идёт в отдельном потоке, прогресс публикуется в `treeScan` основного JSON.
  - Id выполненного запроса хранится в `wsl-tree.json`: после перезапуска агент сканирование не повторяет, а неудачный запрос не перезапускает по кругу.
  - Агент добавляет свой каталог в `sys.path`, чтобы `treescan` импортировался при любом способе запуска.
- **Приложение.**
  - `TreeModels.cs` — модель дерева. `MaxDepth = 1024`: при стандартных 64 вложенные цепочки вроде `node_modules` не разбирались бы.
  - `Treemap.cs` — раскладка squarified (Bruls и др., 2000) и контрол с отрисовкой в кэш-битмап, подсветкой наведения и выделения, подписями блоков верхнего уровня.
  - `DiskMapForm.cs` — окно: карта, вкладки «Содержимое» и «Типы файлов», навигация. Окно открывается пунктом трея «Карта диска WSL…» и при первом открытии само запрашивает сканирование.
  - В csproj копируются все `wsl/*.py`.

### Проверка

- Реальный `/` в Ubuntu: 329 865 файлов, 47.50 из 47.57 GiB насчитано, 0.07 GiB «не учтено», 1.1 с, `wsl-tree.json` 0.42 MB.
- Сквозной прогон агента: запрос подхвачен, прогресс виден, `done`; после перезапуска повторного сканирования нет.
- Отрисовка проверена скриншотами настоящего `DiskMapForm` вне экрана (отдельная программа через reflection). По ним исправлено:
  - файлы без расширения (модели Ollama, большой файл `.comfyui`) были серыми и не различались, теперь получают свой цвет наравне с остальными типами;
  - добавлены подписи «имя + размер» на крупных блоках.
- Тесты: C# 29 (раскладка: площади, границы, отсутствие перекрытий, пропорции, порядок; дерево: глубина 300, пути, валидация схемы); Python `test_treescan.py` (жёсткие и символические ссылки, свёртка мелочи, «не учтено», вытеснение из топ-K без потери байт).
- Побочная проверка из прошлой записи: при жёстком завершении приложения (`Stop-Process`) агент в WSL завершился сам — сработало закрытие stdin.

### Не сделано

- Диски Windows на карте (обход через .NET без админа: для C: минуты).
- Клики проверены только программно; наведение мышью и навигацию в живом окне проверяет пользователь.
- Поиск по карте, «Открыть в проводнике» (`\\wsl$`), объёмная заливка «подушками» как в WinDirStat.

## 2026-11-25 — Ревью и исправление связки Windows ↔ WSL-агент

### Найдено и исправлено

1. **Агент падал при одновременной записи и чтении JSON.**
   - **Подтверждено логом.** В `wsl-agent.log` от 2026-09-21 17:39 есть `PermissionError: [Errno 13]` в `os.replace`, после чего агент упал и перезапустился.
   - **Причина.** `File.ReadAllText` открывает файл без `FileShare.Delete`. Сервер drvfs запрещает rename поверх открытого файла.
   - **Эксперимент.** Файл держали открытым из Windows и делали `os.replace` из WSL. С `FileShare.Read` воспроизводится тот же `PermissionError`, с `ReadWrite | Delete` замена проходит.
   - **Исправление.**
     - Приложение читает JSON через `WslAgentManager.ReadShared` (`FileShare.ReadWrite | Delete`).
     - Агент повторяет `os.replace` до 6 раз.
     - Если запись так и не удалась, агент пропускает один замер, а не падает.
   - Обычный Win32 `File.Move` открытый файл всё равно не заменит. Помогает именно POSIX-семантика drvfs, поэтому C#-юнит-тест для этого невозможен, проверка только через WSL.

2. **Опрос дисков Windows ждал запуска WSL.**
   - **Причина.** `RefreshAsync` ждал `EnsureRunningAsync`: `wsl --list` и три `wslpath` с таймаутами по 20 с. Пока WSL загружался или висел, диски Windows не обновлялись.
   - **Исправление.**
     - Опрос стал синхронным `Refresh`, агент поднимается в фоне (`KeepAgentRunning`).
     - `EnsureRunningAsync` сделан single-flight: параллельный старт двух агентов из таймера и меню исключён.

3. **`du` показывал 0 для каталогов с недоступными файлами.**
   - **Причина.** При коде возврата 1 `du` всё равно печатает итог, но код его отбрасывал. Хуже всего это било по `~/.local/share/containers`: файлы rootless Podman принадлежат подчинённым UID.
   - **Исправление.**
     - Частичный размер сохраняется, ошибка помечается «Частично…».
     - Используется `du -skx`.
     - Для хранилища Podman, если `podman` установлен, запускается `podman unshare du`.

4. **Анализ каталогов повторялся при каждом старте агента, а результат терялся.**
   - **Причина.** Файл запроса не удаляется, а агент начинал с пустым `last_request`.
   - **Исправление.**
     - Агент пишет в JSON `analysisRequestId`, но только завершённого анализа.
     - При старте агент восстанавливает его вместе с результатами (`load_previous`).
     - Второй анализ не запускается, пока идёт первый.

5. **Статус WSL зависел от текста, а не от данных.**
   - **Причина.** Сравнения `StartsWith("WSL недоступен")` и `== "работает"` могли показать «недоступен» при свежих метриках.
   - **Исправление.**
     - Появился `IsWslFresh`: свежие данные важнее последнего сообщения запускатора.
     - Код выхода агента 2 («уже запущен», `flock` занят) больше не считается сбоем: нет экспоненциальной задержки, повторная проверка через 120 с.

### Гипотеза не подтвердилась

- **Сирота-агент после `Process.Kill`.** Предполагалось, что убитый `wsl.exe` оставляет живой `python3` внутри Linux. Эксперимент на Ubuntu/WSL2 показал обратное: при убийстве `wsl.exe` Linux-процесс завершается в обоих режимах stdin.
- **Что всё же сделано, для надёжности.**
  - Агент запускается с `--exit-on-stdin-eof`, приложение держит stdin открытым.
  - При остановке приложение сначала закрывает stdin (штатный выход занял 24 мс, код 0) и только через 3 с убивает процесс.
  - Это закрывает сценарий, когда падает само приложение и `wsl.exe` остаётся без родителя. Этот сценарий не проверялся.
